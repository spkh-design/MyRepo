## Вопрос 1. Какие HTML5-атрибуты используются для клиентской валидации и какую функциональность они предоставляют?
Основные атрибуты: required (поле обязательно для заполнения), minlength/maxlength (минимальная/максимальная длина текста), min/max (границы для чисел, дат, диапазонов), step (шаг изменения числовых значений), type (email, url, tel, number, date и т.д. – задаёт формат и встроенную проверку), pattern (регулярное выражение для проверки значения). Они позволяют браузеру автоматически проверять данные до отправки формы и показывать пользователю стандартные сообщения об ошибках без JavaScript.

## Вопрос 2. В чем разница между novalidate атрибутом формы и отключением валидации через JavaScript?
novalidate – это HTML-атрибут формы, который полностью отключает встроенную браузерную валидацию при отправке: браузер не проверяет required, pattern, type и не показывает стандартные подсказки. Отключение через JavaScript (например, form.noValidate = true или удаление атрибутов у полей) делает то же самое, но динамически, после загрузки страницы или по событию. Разница в основном в моменте применения: novalidate задаётся в разметке, JS-отключение – во время выполнения и может быть условным (например, только для определённых сценариев).

## Вопрос 3. Как правильно связать label с полем ввода и почему это важно для доступности?
Два способа: обернуть поле в label или связать через атрибуты for у label и id у input:

label for="email" – Email
input type="email" id="email" name="email"

Это важно для доступности: скринридеры зачитывают подпись поля, при клике на label фокус попадает в input, увеличивается кликабельная область (особенно для чекбоксов и радиокнопок). Без связи пользователи скринридеров не понимают, что за поле перед ними.

## Вопрос 4. Какие типы полей input наиболее подходят для разных видов данных (email, телефон, пароль и т.д.)?
- type="email" – email: браузер проверяет формат и на мобильных показывает клавиатуру с @;
- type="tel" – телефон: клавиатура с цифрами, формат не проверяется автоматически (нужен pattern);
- type="password" – пароль: скрывает вводимые символы;
- type="number" – числа: стрелки, проверка min/max/step;
- type="url" – ссылки: проверка формата URL;
- type="date", type="time", type="datetime-local" – дата и время: нативные пикеры;
- type="search" – поиск: дополнительная кнопка очистки;
- type="checkbox"/type="radio" – булевы значения и выбор из вариантов.

## Вопрос 5. Как работает валидация с помощью pattern атрибута и в каких случаях его следует использовать?
pattern принимает регулярное выражение, которому должно соответствовать значение поля целиком (браузер автоматически добавляет якоря ^...$). Если значение не подходит – форма не отправится и появится сообщение об ошибке. Пример:

input type="text" pattern="[0-9]{3}-[0-9]{3}" title="Формат: 123-456"

Использовать стоит для простых форматов: почтовый индекс, номер телефона, код, логин. Не стоит перегружать сложными regex – это ухудшает UX и поддерживаемость; сложные проверки лучше делать на JS и на сервере.

## Вопрос 6. Какие события JavaScript используются для реализации валидации в реальном времени и почему?
Основные: input (срабатывает при каждом изменении значения – оптимально для мгновенной проверки), blur/focusout (когда пользователь ушёл с поля – удобно, чтобы не ругать за недописанное), change (при подтверждении изменения), submit (финальная проверка перед отправкой). input чаще всего используют для «живой» валидации, потому что он реагирует сразу, но при этом не мешает вводу, если показывать ошибку мягко. Комбинация blur + input даёт баланс: не показываем ошибку, пока пользователь ещё печатает, но обновляем её после первого «касания».

## Вопрос 7. Как обеспечить доступность сообщений об ошибках для пользователей скринридеров?
Связать сообщение с полем через aria-describedby, добавить aria-invalid="true" при ошибке, использовать role="alert" или aria-live="polite" для контейнера с ошибкой, чтобы скринридер зачитал её при появлении. Текст ошибки должен быть конкретным и находиться рядом с полем. Пример:

input type="email" id="email" aria-describedby="email-error" aria-invalid="true"
p id="email-error" role="alert" – Введите корректный email

Также важно не полагаться только на цвет – нужен текст или иконка.

## Вопрос 8. В чем преимущества использования fieldset и legend для группировки полей формы?
fieldset логически объединяет связанные поля (например, группу радиокнопок или адрес), а legend даёт этой группе заголовок. Преимущества: скринридеры зачитывают legend при входе в группу, пользователь понимает контекст; визуально группа выделяется рамкой (можно стилизовать); улучшается семантика и навигация по форме. Особенно важно для групп radio/checkbox, где без legend непонятно, что именно выбирает пользователь.

## Вопрос 9. Как реализовать кастомную валидацию для сложных случаев (например, подтверждение пароля)?
Использовать Constraint Validation API: setCustomValidity(), checkValidity(), reportValidity(). Пример:

const pass = document.getElementById('pass');
const confirm = document.getElementById('confirm');

confirm.addEventListener('input', () => {
  if (confirm.value !== pass.value) {
    confirm.setCustomValidity('Пароли не совпадают');
  } else {
    confirm.setCustomValidity('');
  }
});

При несовпадении форма не отправится, а браузер покажет заданное сообщение. Также можно слушать submit и вручную проверять условия, добавляя классы ошибок и тексты.

## Вопрос 10. Какие методы CSS используются для визуального отображения состояний валидности/невалидности полей?
Псевдоклассы :valid и :invalid – применяются к полям с корректным/некорректным значением. :required – для обязательных. :focus, :focus-visible – для подсветки активного поля. :user-invalid (и :user-valid) – более мягкий вариант: срабатывает только после взаимодействия пользователя. Дополнительно – :placeholder-shown для проверки, пустое ли поле. Пример:

input:invalid:not(:placeholder-shown) {
  border-color: red;
}
input:valid {
  border-color: green;
}

Важно дублировать цвет текстом или иконкой для доступности.
